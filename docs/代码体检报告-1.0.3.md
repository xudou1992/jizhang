### P0-2 记账金额被截断，573/9999 个常见金额会少记 1 分

`jizhang-native/app/src/main/java/com/jianji/jizhang/ui/add/AddScreen.kt:79`

```kotlin
val cents = amountText.replace(",", "").toDoubleOrNull()?.let { (it * 100).toLong() } ?: 0L
```

`.toLong()` 是**截断**，不是四舍五入。浮点乘法本身就带误差，`1.15 * 100` 得到
`114.99999999999999`，截断后存 114 分。

穷举 0.01 ~ 99.99 全部两位小数（9999 个），**573 个会被记错**：

| 你输入 | 实际存进库 |
|---|---|
| 0.29 | 0.28 |
| 1.15 | 1.14 |
| 2.05 | 2.04 |
| 2.26 | 2.25 |

同一个仓库里另外两处是对的，说明这是漏改：

- `ui/detail/TxDetailScreen.kt:181` 与 `:349` → `(it * 100).roundToLong()` ✅
- `data/backup/BackupCodec.kt:85`（恢复入库）→ `roundToLong()` ✅
- `AddScreen.kt:79`（日常记账主路径）→ `toLong()` ❌

**这是日常使用频率最高的一条路径**，每 17 笔就有一笔金额偏差 1 分。

修复：改成 `roundToLong()`，并抽一个 `parseYuanToCents(text): Long` 放
`data/` 里，三处共用，避免以后再分叉。

### P0-3 新建分类 / 换个颜色之后，颜色变成全透明（圆点看不见）

涉及 4 处：
- `ui/manage/CategoryManageScreen.kt:261`（新建时默认色）
- `ui/manage/CategoryManageScreen.kt:304`（点色板）
- `ui/manage/AccountManageScreen.kt:324`、`:367`（同上）

```kotlin
var selectedColor by remember {
    mutableStateOf(initial?.color ?: CategoryPalette.first().value.toLong())
}
...
val c = color.value.toLong()
```

`Color` 是 `value class`，其 `value` 是**已打包的 64 位 ULong**（等于 `argb shl 32`）。
而 `Color(color: Long)` 工厂内部**会再左移 32 位**：

```kotlin
public fun Color(color: Long): Color = Color((color shl 32).toULong())
```

所以 `Color(x.value.toLong())` 实际是 `argb shl 64` → 64 位里溢光 → **0**，
即 `Color(0UL)` = 全透明。渲染侧 `Color(category.color)` 得到的就是一个透明圆。

具体表现（按触发条件分）：

| 操作 | 结果 |
|---|---|
| 从 migration.json 灌进来的老分类/账户 | 正常（color = 0xAARRGGBB） |
| 编辑已有分类，只改名字 | 正常（原值原样回存） |
| **新建分类 / 新建账户** | 颜色 = 0，圆点与首字全透明 |
| **在色板里点一下换色** | 同上，变透明 |

只有动了色板才会踩到，所以容易漏过自测。

附带影响：`BackupCodec.export` 用 `it.color.toInt()` 导出颜色，对这种值会取出
低 32 位 = 0，于是**备份文件里颜色也是 0**，恢复回来同样是透明的。

修复：统一用 `color.toArgb().toLong()`（`toArgb()` 返回 0xAARRGGBB 的 Int），
存进实体的 `color` 与老数据格式一致。

### P0-4 删光所有账单后重启 App，608 笔旧数据会"复活"

`jizhang-native/app/src/main/java/com/jianji/jizhang/data/Ledger.kt:183-185`

```kotlin
suspend fun seedIfNeeded(context: Context, db: LedgerDb) {
    val dao = db.dao()
    if (dao.txCount() > 0) return
    // …灌入 assets/migration.json
}
```

判定条件是「**库里有没有账单**」，而不是「**有没有灌过种子**」。两者在多数时候
等价，但一旦账单数归零就分叉了：

- 用户手动删完所有账单 → 下次启动，608 笔 2026 年的旧账全部回来；
- 从一份空备份恢复 → 同上；
- 迁移包被清空后重新灌入 → 同上。

对一个"账要记得准"的 App 来说，用户明确删掉的数据自己长回来是很严重的行为。

修复：把"已灌种子"作为一个**只写一次**的标记，与账单数解耦。两种做法：
- DataStore 里加 `seeded = true`；
- 或在 `RoomDatabase.Callback.onCreate` 里灌（数据库只在真正创建时调一次）。

### P2-4 自动备份防抖的两个逻辑漏洞

`LedgerViewModel.kt:82-91`：

```kotlin
val enabled = app.nutstoreSettingsFlow().first().enabled
if (!enabled) return@launch
delay(AUTO_BACKUP_DEBOUNCE_MS)          // 3 分钟

```

`enabled` 在 `delay` **之前**读。用户在 3 分钟内关掉自动备份开关，这次上传照样

和 `deleteTx()`（`:102`）都调了 —— 编辑一笔账单不会触发同步。
