## 一、迁移安全

原来 `exportSchema = false` 且挂着 `fallbackToDestructiveMigration()`：当前 `version = 1`
用不上迁移，但**今后任何一次加字段都会静默清空整个库**（608 笔种子 + 用户之后记的全部），
而且没有 schema 基线，想写 Migration 也无从下笔。

改了三处：

1. `data/Ledger.kt`：`exportSchema = true`；新增 `MIGRATIONS` 空数组并 `.addMigrations(*MIGRATIONS)`
2. `app/build.gradle.kts`：`ksp { arg("room.schemaLocation", "$projectDir/schemas") }`
3. 产物 `app/schemas/com.jianji.jizhang.data.LedgerDb/1.json`（4160 字节）提交进仓库

`Ledger.kt` 里写明了加字段的标准动作：改实体 → `version` 加 1 → 构建一次让新 schema 落盘
→ 写 `Migration(旧, 新)` → 挂到 `MIGRATIONS`。**只要 MIGRATIONS 为空且版本变了，
Room 找不到迁移就会走 destructive 兜底，那是丢数据。**

`LedgerSchemaTest` 会守住这条底线：schema 目录不存在、没有 json、或者三张表/六个关键列
对不上，测试直接红。

## 三、⚠️ 环境坑：中文工作区路径 + Gradle `@argfile`

**症状**：6 个测试类**全部** `initializationError`，报
`java.lang.ClassNotFoundException: com.jianji.jizhang.data.MoneyTest`。
看起来像「测试类没编译出来」，但 `.class` 文件明明都在
`app/build/tmp/kotlin-classes/debugUnitTest/` 下。

**根因链**：

1. `gradle.properties` 里显式给守护进程设了 `-Dfile.encoding=UTF-8`
   （Gradle 模板的样板行，从最初那次提交就在）
2. Gradle 用**守护进程的默认字符集**把 worker 的类路径写进参数文件
   `C:\Users\50454\.gradle\.tmp\gradle-worker-classpath*.txt`，于是中文路径
   `D:\记账软件\…` 被写成 **UTF-8 字节**
3. JDK 启动器在 **JVM 起来之前**就展开了 `@argfile`，用的是**平台 ANSI 代码页**
   （本机 CP936/GBK）—— 于是中文被解成乱码，类路径整条失效

证据（同一个文件的两次快照，中文部分的原始字节）：

```
22:38 的 argfile： e8 ae b0 e8 b4 a6 e8 bd af e4 bb b6   ← UTF-8 的「记账软件」
22:44 的 argfile： bc c7 d5 cb c8 ed bc fe               ← GBK  的「记账软件」
```

**排查中踩过的坑（下次别再踩）**：

- 用最小复现隔离时，`@argfile` 里**反斜杠是转义符**。写单反斜杠路径会被吃掉，
  于是 UTF-8 和 GBK 两份 argfile **都**失败，很容易得出「跟编码无关」的错误结论。
  必须用正斜杠，或写成 `\\`。
- `-Dsun.jnu.encoding=UTF-8` / `-Dfile.encoding=UTF-8` 加在命令行上**都没用** ——
  启动器在 JVM 启动前就解码完了，命令行上的 `-D` 改不了它。
- 最直接的判断方法是**读 Gradle 写的那份 argfile 的原始字节**，而不是猜。

**修复**：`gradle.properties` 的 `org.gradle.jvmargs` 去掉 `-Dfile.encoding=UTF-8`，
让守护进程跟随平台编码 —— 与启动器**按构造对齐**，比硬写 GBK 更正确，对纯 ASCII 路径
无影响。

**排除的副作用**（都实测过）：

- 测试报告 HTML 仍是**合法 UTF-8**，中文正常（Gradle 写报告用的是显式 UTF-8）
- Kotlin / KSP 跑在**独立的 Kotlin 守护进程**（`kotlin.daemon.jvmargs`，不继承
  `org.gradle.jvmargs`），字符集本来就跟平台一致，不受影响
- AAPT2 是原生程序、XML 按 UTF-8 解析；APK 里 `application-label:'简记'` 正常
- 源码里的中文字面量在 class 文件里仍是合法 UTF-8（抽查了「纯黑背景」「点按查看详情」
  「简记」「本月」）

## 四、日期选择器限制未来日期

`ui/components/Pickers.kt` 的 `DateField` 加了 `SelectableDates`：日期不能超过今天，
年份不能超过今年。记账场景补记旧账是常态，但记未来的账基本是误操作。

```kotlin
val today = LocalDate.now()
val todayUtcDay = localDateToUtcDay(today)
val state = rememberDatePickerState(
    initialSelectedDateMillis = localDateToUtcDay(localDate(dateTime)),
    selectableDates = remember(todayUtcDay, today.year) {
        object : SelectableDates {
            override fun isSelectableDate(utcTimeMillis: Long): Boolean = utcTimeMillis <= todayUtcDay
            override fun isSelectableYear(year: Int): Boolean = year <= today.year
        }
    },
)
```

注意 `selectedDateMillis` 是「UTC 当日 0 点」，所以比较必须走 `localDateToUtcDay()`
换算出来的 UTC 当日值，不能拿系统时区的 `now()` 直接比 —— 否则东八区会差一天。

## 五、测试暴露的 2 处问题（都不是代码 bug）

首次跑通后 `ColorCodecTest` 挂了 2 个用例，期望值是 `0xFFE5484DL`（正数），
实际拿到 `-1750963`。查下来是**测试写错了**，不是代码：

- `toStoredLong()` = `toArgb().toLong()`，而 `toArgb()` 返回 `Int`，不透明色
  （alpha = 0xFF）最高位为 1，**符号扩展成 Long 就是负数**
- `assets/migration.json` 里 608 笔种子的 `color` **全是负数**（`-1096636`、`-15681151` …），
  `BackupCodec` 的 `color.toInt()` 也是同一套表示 —— 全项目是一致的

**所以正确的动作是改测试和文档，而不是给 `toStoredLong()` 加 `and 0xFFFFFFFF`。**
加了之后新写入变正数、存量仍是负数，渲染看不出差别（`Color(Long)` 只取低 32 位），
但「这个颜色有没有变」这类比较会悄悄失真。

已把契约写进 `ColorCodec.kt` 的注释和 `ColorCodecTest` 的两条断言（位模式 + 表示唯一性）。
